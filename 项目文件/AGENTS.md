# 项目协作约定

本文件是可复用模板。初始化项目时，根据用户要求和项目实际情况补充约定；已有项目约定不得直接覆盖。用户针对当前任务的明确指令优先。

- 项目名称：【填写】
- 目标和主要交付：【填写】
- 当前阶段：【填写，例如规划、实现、维护】
- 运行环境、平台或技术约束：【填写；未知项标待确认】
- 必须保留的文件、数据或外部系统：【填写；无则写无】
- 远程仓库和推送权限：【填写；未知时先保留本地提交】

## 节点实施

1. 每次编码、继续中断任务或分配任务前，读取本文件、`docs/项目思路与技术方案.md`或项目实际指定的方案文档、`docs/项目节点实施与验收计划.md`的总规则、当前节点、引用的设计与前置验收结果，核对工作区和已有成果。
2. 只实施用户明确授权的一个节点。计划中列出的其他节点不自动授权；不得提前创建后续节点源码、配置、测试或空壳。节点内需要的小步修复、测试和相关文档属于当前范围。
3. 根据当前节点实现功能、运行必要测试，在节点计划中回填真实过程、版本、指标、失败和证据，按模块小步提交，然后停止等待用户验收。
4. 自测通过不等于用户验收通过；用户验收通过不等于下一节点已经授权。未运行、跳过或失败的必需检查不得记为通过；不编造数据、指标或执行结果。
5. 普通实现选择按项目上下文自行判断。确需改变已约定的验收标准或扩大节点范围时，先说明原因和影响，取得用户确认；修改已验收共享模块时补做受影响的回归检查。
6. 涉及项目思路、技术方案、实现、实验或交付的实质讨论和变化，维护`docs/项目思路与技术方案.md`或项目实际指定的方案文档，并同步当前节点和相关说明；实施时发现影响未来节点，说明影响和建议，未经用户确认不修改未来节点范围或结果。区分计划、已实现、已运行和已验收。历史版本使用Git追溯，不自动建立逐次备份或通用更新记录。

## Git与交付

- 按步骤、按模块拆分可独立复核的小改动，完成必要检查后及时提交；提交前检查工作区和暂存内容，不混入或覆盖无关改动。
- 使用`<type>[(scope)][!]: <description>`。type使用小写英文`feat/fix/docs/style/refactor/perf/test/build/ci/chore/revert`，scope、描述、正文和页脚以中文为主；专有名词与标准标识可保留英文。
- 标题以动作词开头，末尾不加句号；正文和页脚为可选内容，用空行分隔。真实破坏性变更使用`!`或`BREAKING CHANGE:`标明，真实Issue关联保留`Closes #123`等语法。
- 用户明确授权推送时检查远程及分支后推送；未获推送授权时只提交到本地。未经另行授权，不强制推送、不改写已发布历史、不删除用户内容。
- 密钥、个人敏感信息、虚拟环境及项目约定不应入库的大型原始数据、权重和产物不得提交；必要的证据保留路径、版本与哈希。
- 交付时说明做了什么、测试结果、实际效果与限制、证据位置、提交及推送状态；遇阻如实说明，不以推测代替实测。

涉及训练、评测或数据处理的Python入口，在适用且不违背项目已有约定时，优先支持选好解释器后在IDE直接运行，提供明确默认配置，命令行可作为可选方式；首次环境和数据准备与日常运行分开。

详细规范见`docs/开发与Git协作规范.md`。当前文件只是项目约定，不因存在或被读取而自动授权任何编码任务。
